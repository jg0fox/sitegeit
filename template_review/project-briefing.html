1. What Is Sitegeit

Sitegeit is a desktop-primary SaaS pipeline (with responsive mobile support) that:

  1. Discovers local businesses that don't have websites (via Google Places API)
  2. Enriches business data using Claude AI (brand voice, services, value proposition, etc.)
  3. Generates conversion-optimized preview websites & landing pages (themed, AI-written content)
  4. Drafts personalized outreach emails (3-email sequence per prospect)
  5. Manages the full client lifecycle (review, send, track engagement, convert to paying client)

The product is an internal tool for a one-person agency. The user discovers local businesses without web presence, the pipeline automatically generates everything needed to pitch them, and the user reviews/approves before outreach.

3. Architecture & Data Flow

The high-level flow:

User action (UI)
    → API route (Next.js)
        → QStash publish (queue job)
            → Worker endpoint (serverless function)
                → Claude AI / Supabase writes
                    → Supabase Realtime push
                        → UI auto-updates

Key Architectural Decisions

  • All AI processing is async — never blocks the UI. Pipeline workers run as serverless functions triggered by QStash.
  • Worker chain pattern — each worker queues the next stage on completion. There's no orchestrator; it's a simple sequential chain.
  • Supabase Realtime — the pipeline page subscribes to postgres_changes on the businesses table and auto-refreshes when status changes.
  • QStash signature verification — all worker routes use verifySignatureAppRouter from @upstash/qstash/nextjs in production; skipped in dev.
  • Generated sites are rendered dynamically — no static generation or separate deployment. Content is stored in Supabase and rendered on-demand via /sites/[slug] routes.
  • Subdomain routing is dormant — the middleware supports *.sitegeit.com subdomains, but currently everything runs on seitgeit.vercel.app with path-based routing (/sites/{slug}).

4. Pipeline Worker Chain (Deep Dive)

This is the core of the product. When a user adds businesses to the pipeline, this chain runs automatically:

User clicks "Add to pipeline" → POST /api/discover/add-to-pipeline
↓ publishes QStash message
Stage 1: Enrich — /api/workers/enrich
Calls Claude with business data + Google Place details. Extracts: brand_voice, value_proposition, services[], target_audience, service_area, review_sentiment, brand_colors. Updates businesses table. Status: discovered → enriching → enriched.
↓ publishToWorker('generate-site')
Stage 2: Generate Site — /api/workers/generate-site
Calls Claude with enriched data + theme config + content KB. Generates: homepage_content (hero, services, testimonials, about, CTA), seo_meta (title, description, schema.org). Inserts/updates generated_sites table. Status: enriched → generating.
↓ publishToWorker('deploy')
Stage 3: Deploy — /api/workers/deploy
Marks the generated_sites record as deploy_status = 'live'. (For MVP, sites are rendered dynamically, so "deploy" is just a status update.)
↓ publishToWorker('generate-email')
Stage 4: Generate Email — /api/workers/generate-email
Two-step: (1) Generates a landing page via Claude (headline, strategy, site preview, pricing tiers, CTA) → inserts into landing_pages. (2) Generates a 3-email outreach sequence via Claude (initial + 2 follow-ups) → inserts into outreach_emails. Creates a notification for the user. Status: → review_ready.
↓
Pipeline complete. User reviews emails in the Email Review screen.

Worker Route Pattern

Every worker follows the same pattern:

// src/app/api/workers/{stage}/route.ts
import { verifySignatureAppRouter } from '@upstash/qstash/nextjs'

async function handler(request: Request) {
  const data = await request.json()
  const businessId = data.businessId as string

  // ... do work ...

  // Chain: queue next stage
  const messageId = await publishToWorker('next-stage', { businessId })

  return NextResponse.json({ success: true })
}

// Production: QStash signature verification wrapper
// Development: raw handler (no verification)
export const POST = process.env.NODE_ENV === 'development'
  ? handler
  : verifySignatureAppRouter(handler)

Worker Idempotency

Workers are idempotent (QStash retries up to 3x on failure):

  • generate-site: Checks for existing generated_sites record → updates if exists, inserts if not.
  • generate-landing: Same upsert pattern for landing_pages.
  • generate-email: Deletes existing draft emails before inserting new ones.

Timing

Full pipeline: 2-4 minutes end-to-end. Enrich ~30s, Generate site ~60s, Deploy ~1s, Generate email ~60s. Plus QStash delivery latency (~1-2s between stages).

12. Known Gotchas & Debugging Lessons

QStash Signature Verification

Use verifySignatureAppRouter from @upstash/qstash/nextjs — it wraps the handler. Don't try to manually verify. In dev mode, workers skip verification entirely.

Vercel Env Var Trailing Newlines

Both ANTHROPIC_API_KEY and NEXT_PUBLIC_SUPABASE_ANON_KEY had trailing \n that caused silent failures. The Supabase one showed as %0A in WebSocket URLs. Always use printf '%s' when piping values to Vercel CLI.

DOMException Not Available in Node.js

The web-detection service originally caught DOMException, which doesn't exist in Node's server runtime. Use generic catch blocks instead.

Google Places API: "Legacy" Not "New"

The project uses the legacy Google Places API. The Cloud project needs both "Geocoding API" and "Places API" (not "Places API New") enabled. The legacy API uses type (singular) in details requests, not types.

Supabase Auth Trigger

The handle_new_user() trigger auto-creates a public.users row when someone signs up via Supabase Auth. If a user signed up before this trigger existed, their profile row must be manually inserted.

deploy_url Format

The deploy_url column in generated_sites and landing_pages stores slugs only (e.g. 1-mile-auto-repair), not full domains. Both the page.tsx and layout.tsx must query by slug, not by full domain. A mismatch between these caused a 404-with-content bug.

CSS Variable Name Collision

--space-section was used for both max-width AND section padding. When the theme set it to 4rem (for padding), containers collapsed to 64px wide. Fixed by adding --container-max-width as a separate variable.

Worker Routes Skip Supabase Auth

Routes under /api/workers/* are called by QStash, not by users. The auth middleware in src/lib/supabase/middleware.ts excludes /api/workers and /sites paths from auth redirects. Workers use getAdminClient() (service role key) instead.

14. Coding Conventions

General

  • Framework: Next.js App Router. Server Components by default, 'use client' only when needed (interactivity, hooks, browser APIs).
  • Styling: Tailwind utility classes. Custom CSS only in generated site components (inline styles with CSS variables).
  • Icons: Material Symbols Outlined, always with className="material-symbols-outlined" and explicit font-size via inline style.
  • Components: Functional components only. Props interfaces defined inline or as separate interface above the component.
  • Imports: @/ path alias for src/. Supabase server client via createClient from @/lib/supabase/server.
  • Data fetching: Server Components fetch data directly (no API calls from server components). Client Components use createBrowserClient or fetch API routes.

Supabase Patterns

// Server Component (authenticated user context)
import { createClient } from '@/lib/supabase/server'
const supabase = await createClient()
const { data: { user } } = await supabase.auth.getUser()

// Worker / Admin (service role, bypasses RLS)
import { getAdminClient } from '@/lib/supabase/admin'
const supabase = getAdminClient()

// Client Component (browser)
import { createBrowserClient } from '@supabase/ssr'
const supabase = createBrowserClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
)

// Generated site pages (server, no auth, service role)
import { createClient } from '@supabase/supabase-js'
const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!,
  { auth: { persistSession: false } }
)

  • Errors: [What failed]. [Why]. [What to do].
  • Empty states: Explanation + CTA.
